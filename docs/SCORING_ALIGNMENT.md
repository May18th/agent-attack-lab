# 比赛评分细则对照与证据准备

更新时间：2026-10-13

适用范围：这是一份比赛对“项目作品”的评审细则，不是攻防实验室产品内的评分规则。本文只用于整理参赛材料和证据；不定义战局分数、Agent 质量分、用户排名或产品内部评分。攻防实验室另有独立的[内部评分规则](INTERNAL_SCORING.md)，分别评价攻击 Agent 和防守 Agent 的输出结构、执行及可审计性，不套用比赛分值，也不代表漏洞检测准确率或实际修复效果。后台运行统计与内部评分均不能替代平台侧访问量等比赛证据。

本文据此整理项目可用证据、当前差距和后续验收动作。它是准备清单，不代表评委已评分，也不把计划或规则模拟写成已完成成果。

| 评分项 | 项目可对应的能力/材料 | 当前边界与待补证 |
|---|---|---|
| 创新性（25） | 基于开源 ACPs SDK 二次开发；Leader 编排攻击与防守两个独立 Agent；采用 AIP JSON-RPC；逐调用事件携带 correlationId，便于把交互与结果对应起来。 | 是否达到“创新”由评委判断；需准备架构图和一次可复现的互联演示。 |
| 需求分析（10） | 面向智能体互联场景，支持主题输入、难度选择、攻击样本、证据型防守发现、风险与修复建议；下文给出按当前系统抽象的需求基线。 | 需求角色和验收流程来自现有产品功能归纳，尚无外部用户访谈证据；当前规则样本是受控演示，不代表客户生产问题。 |
| AI 技术应用（20） | ACP/AIP 多 Agent 调度、mTLS 客户端配置、来源标记和失败留痕；本地规则提供无模型情况下的确定性演示。 | 当前未接入外部 LLM；`reportedLlmResultCount` 仅按 Partner 返回的 `agentSource` 统计，不是独立模型调用证明。不得将规则兜底包装成模型结果。 |
| 项目实施（15） | 后端 API、持久化事件、Redis 可选缓存、隔离验收脚本和自动化测试；生产环境已有此前单独记录的部署与互联验收。 | 本次调用追踪/统计改动目前仅在本机工作区，须通过完整测试、代码审核后另行部署；部署前不可声称已上线。 |
| 应用成效（10） | 后台统计当前已保存战局、Agent 执行次数、ACP 请求成功/失败、Partner 规则兜底及平均调用耗时。 | 统计是本系统已保存数据口径；它不等同平台访问量、独立用户数或真实目标修复数。评分若要求梧桐平台访问量，应另取平台侧可核验数据。 |
| 总结与展望（10） | 可从互联稳定性、规则兜底边界、真实模型评估和访问数据缺口形成复盘。 | 答辩材料需总结已验证结果、限制和下一步，不把待办写成成果。 |
| 附加分（10） | 仓库提供源码、启动/验证脚本及接口说明；可用事件与来源字段支持演示互联调用过程。 | 一键部署须在干净环境实测；完整演示视频需人工录制并展示平台发现、互联和访问；平台访问次数应由平台侧报表或可审计数据提供，不能用战局数代替。 |

## 需求基线

以下是依据现有系统能力整理的项目范围，不声称来自外部客户访谈：

| 编号 | 使用需求 | 当前验收证据 |
|---|---|---|
| R1 | 演示者可选攻防主题和难度，发起一场受控测试。 | `POST /battles` 参数校验及 low/mid/high 隔离验收。 |
| R2 | 参与者能看到攻击 Agent 生成的样本，并知道它来自本地规则还是独立 ACP Agent。 | `attackerOut.samples`、`agentSource` 和调用事件。 |
| R3 | 防守 Agent 对每个样本给出证据命中、条件性风险和修复建议。 | `defenderOut` 字段及证据/范围约束测试。 |
| R4 | 评审或维护者可复核每个 Agent 调用是否成功、耗时多少，以及它对应哪一轮结果。 | `agent.call.*`、结果事件中的 `correlationId`、`GET /battles/{id}/events`。 |
| R5 | 维护者能区分战局数、Agent 执行次数和 ACP 请求次数，定位失败与规则兜底。 | `GET /dashboard/summary` 新统计字段。 |

验收环境限于授权的演示系统和隔离测试数据；不对未授权目标执行攻击，也不把修复建议称为已经修复。

## 新增的调用证据口径

- `agent.call.started` 与 `agent.call.completed` / `agent.call.failed` 事件以同一 `correlationId` 配对；关联 ID 同时作为该次 AIP session ID。
- 攻击样本事件和每轮防守结果事件回填对应的 `correlationId`，可从结果追溯到调用状态、Agent 角色和耗时。
- `GET /dashboard/summary` 中 `agentExecutionCount` 是已完成/失败的 Agent 执行次数；`acpRequestCount` 是远端 ACP 请求次数；`acpSuccessCount` 是成功收到并通过结构校验的 ACP 响应；`acpFailureCount` 是失败请求数。
- `acpRuleFallbackCount` 是 Partner 响应来源报告为 `acp-rule-fallback` 的次数；`localRuleExecutionCount` 是未配置 ACP URL 时本地规则执行次数。
- `reportedLlmResultCount` 只代表远端响应字段声明 `acp-llm`；没有模型供应方遥测或独立凭证时，不作为真实模型调用证明。
- 上述统计按保留中的战局事件聚合。删除战局会一并删除其事件，因此是当前留存数据统计，不是永久累计计数。
- `X-Battle-ID` 用于 502 ACP 调用失败后定位已保留的失败战局；跨域读取响应头需 CORS 暴露该字段。

## 比赛材料验收清单

1. 本地完成后端完整测试、前端兼容性和隔离环境端到端验收。
2. 将调用追踪改动审核并部署到隔离或生产环境；记录部署提交、时间、测试战局 ID 和请求 ID。
3. 用真实平台账号演示 Discovery 查询、AIP 互联及至少一场访问；保留授权范围内的截图/日志。
4. 单独录制演示视频，画面包含发现、互联、访问、事件 correlationId 与结果来源。
5. 从梧桐平台取得访问数据；明确时间窗口、去重口径和数据导出来源，不以本项目战局数替代。
6. 答辩说明当前 Partner 使用规则兜底的事实，以及接入真实模型、真实业务遥测和修复复测仍需的条件。
